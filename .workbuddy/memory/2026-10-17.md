## Network demo 多线程同步：数据竞争分析 + 锁 vs __atomic 建议
- 用户问 `g_running_epoch` 是否要加锁。结论：`g_running_epoch` 本身**不用锁**——只被主线程(button_cb)写，worker 只在 `pthread_create` 之后读一次(`my_epoch`)，POSIX happens-before 保证可见。
- 但 `g_epoch`(主写/worker读末尾) 和 `g_running`(主+worker都写、主读) 是**真实数据竞争**(无锁/无原子)；因声明 `volatile` + ARM 对齐 int 原子读写，实践不会出错但严格 C 模型是 UB。
- 用户问用锁还是 `__atomic_*`。建议 **`__atomic_*`(GCC 内置, gnu99 可直接用, 无需升 gnu11)**：
  1) 避免死锁/重入坑——`g_mtx` 已被 `log_append` 内部使用，为保 int 再加锁易在"持锁区调 log_append"时非递归锁死锁；
  2) lock-free 零开销，更适合嵌入式；3) 无需改 -std。
- 推荐混合方案：`g_log_buf` 继续用 `g_mtx`(字符数组必须互斥)；三个 int(g_running/g_epoch/g_running_epoch) 改用 `__atomic_*`(SEQ_CST)，按钮回调/worker 首尾/watchdog 读全部替换；声明里的 `volatile` 可去掉。待用户定夺是否实施。
