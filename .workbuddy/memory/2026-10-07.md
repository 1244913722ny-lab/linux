## 更正：体积不是根因（13:40 复核）
- `file/rootfs/rootfs.img` 在 git 中**已是 LFS 指针**(132B, version https://git-lfs.github.com/spec/v1)，img 走 LFS 配置正确。
- 待推送 pack 实测仅 ~151MB（du 看到的 3.1GB 多为 .o 等被 gitignore 的编译产物，未进 git）。**体积不是推送失败原因。**
- 沙箱实测：`git ls-remote`/`curl github` 可达(200)，但 `git push` 报 `Failed to connect to github.com port 443`（沙箱网络不稳，非本机结论）。
- 结论：用户本机 push 失败的真实瓶颈是**认证或网络/代理**，不是体积。img 通过 LFS 完整入库的机制已具备，只需让 push 真正连上 GitHub 并完成认证。

- 下一步：让用户确认本机报错类型（认证 / 代理连接 / 其他），再给对应修复（SSH 最稳 / 配 git proxy / 重登 GCM）。

## 最终根因(用户贴出真实报错)
- 用户本机 push 真实报错：`remote: error: File file/uboot-start/full_sd.img is 1024.00 MB; this exceeds GitHub's file size limit of 100.00 MB` + `GH001: Large files detected` + `pre-receive hook declined`。
- 结论：**连接和登录都正常**（push 已跑到 Writing objects 146MiB、远端 Resolving deltas 都完成了），唯一阻塞项是 `full_sd.img`=1024MB 超过 GitHub 100MB 硬上限。另一文件 `flash0.bin`=64MB 只是警告(<100MB 允许)。
- 历史扫描确认：仓库内唯一 >100MB 的 blob 就是 `full_sd.img`(1024MB)；50~100MB 仅 `flash0.bin`(64MB)。`rootfs.img` 已是 LFS 指针。
- 原因：`full_sd.img` 在配 LFS 之前就以真实 1GB 块提交进历史，未走 LFS。修复=用 `git lfs migrate import` 把这两个大文件改写成 LFS 指针(重写本地3个未推送提交，安全可逆)。
- 沙箱限制：Windows FS 不支持 stash 某些符号链接文件(`file/busybox-1.37.0/_install/bin/arch` open 失败)、443 不通，无法在沙箱完成改写；需用户在自有机器执行。
- 修复命令(用户本机)：`git lfs install` → `git stash`(净树) → `git lfs migrate import --include="file/uboot-start/full_sd.img,file/uboot-start/flash0.bin" --include-ref=main` → `git stash pop` → `git push origin main`。
- 配额提醒：full_sd.img=1GB 会吃满 GitHub LFS 免费额度(1GB 存储+1GB 带宽/月)，克隆也耗带宽；大镜像建议改放 GitHub Releases 或升级 LFS。
