## FLIP 动效 demo：动画「视觉无动效」诊断与修复
- 用户完整日志证明 FLIP 逻辑正确：每张卡 `exec start`=First(当前坐标)、`exec end`=Last(目标槽位)，插值正确；但视觉上卡片瞬移、无滑动。
- 结论：动画逻辑没问题，是**渲染/脏区域未刷新**导致中间帧不显示。本 demo 唯一非标准点是 `flip_exec` 里给卡片加了 `transform_zoom` 缩放变换——LVGL v8 中「transform 对象 + 持续移动 + 局部刷新(40行小缓冲)」组合，移动过程的脏区域刷新易出问题，只在落定时画一帧 → 像瞬移。
- 修复：去掉 `transform_zoom`（纯位移是 LVGL 最稳的动画路径）；`open` 里也不再设初始 zoom。
- 同时加诊断：每卡 `g_ec[]`(exec 调用次数)、`g_shuffle_tick`、`g_force_full_inval`(=1 时每帧 `lv_obj_invalidate(lv_scr_act())` 强制全屏重绘，作为脏区域问题后备开关)。`end` 日志现打印 `frames=` 与 `span=`(动画耗时 tick)。
- 待用户 `make` 复验：若仍无动画，把 `g_force_full_inval` 改 1 再测，可确认是否脏区域失效。沙箱内无 C 编译器，未实编。

## 根因坐实（源码佐证）+ 调试代码清理
- 用户复验：去掉 zoom 后动画正常 → 确认 `transform_zoom` 是根因。
- 源码证据链（LVGL v8.3.11）：
  - `lv_obj_style.c:881`：`transform_zoom != 256` → 对象 `layer_type = LV_LAYER_TYPE_TRANSFORM`。
  - 刷新时 `refr_obj`(`lv_refr.c:964`)：`layer_type==NONE` 走 `lv_obj_redraw`(普通对象直接画屏，局部增量刷新)；否则走 `lv_draw_layer_create`(`lv_refr.c:992`) 离屏图层分支，变换后 blit 回屏。
  - `flip_exec` 的 zoom 取值：v=0 和 v=1024 时 dip=0→zoom=256(NONE，普通路径，可见)；中间帧 zoom=192..255≠256→TRANSFORM 离屏图层路径。在「逐帧移动 + fbdev 局部刷新」组合下该离屏图层中间帧未提交到屏幕，于是只剩首/末两帧可见 = 瞬移。完美解释症状。

## camera_demo 画面放大（用户反馈"画面太小了"）
- 根因：手机默认推 320x240，tjpgd 只能缩（1/1~1/8）不能放，直接显示只占 800x480 屏一小块。
- 方案：`tj_output_cb` 里做**等比最近邻放大**（tjpgd 输出 -> 目标尺寸 g_dec_dw/dh），避开 transform 图层坑。水平用累加器推进源像素下标（避免逐像素除法，QEMU 软解很慢），垂直按比例写多行；dw==w 时走原 1:1 快路径不付开销。
- decode_frame 里：scale 选档后算目标尺寸（宽高比保持，不拉伸），面积倍数超 CAM_MAX_UPSCALE(默认 4) 就每轮缩 1/16 渐近收敛封顶；缓冲 need / dsc.w/h / out_w/h 全用放大后尺寸（**dsc 尺寸错了 LVGL 只画左上角一小块**）。
- 显示区从 `屏高-90` 放宽到 `屏高-40`（info/fps 是浮层不占高度）。800x480 上 320x240 → 586x440。
- `cam_server.js` 网页默认推流分辨率 320x240 → **480x360**（放大倍率降到 1.22，细节更多且更省 CPU；用户可改回）。
- 仍需用户在 WSL 里 make all 验证（WSL 仍被 Program Blacklist 拦截）。
- **踩坑修正（花屏）**：第一版把坐标映射写在 tjpgd 输出回调里 → jd_decomp 是按 MCU 分块回调，rect->left 是块内起点不是整幅列号，导致写错列 + 越界读块 → 满屏花屏。已重构：回调恢复 1:1 只写"源区"，新增 scale_up_nearest() 在回调外整图放大到"显示区"；帧缓冲一次分配两段 [0,dw*dh)+[dw*dh,dw*dh+w*h)；无放大时 dsc.data 直接指源区省掉每帧 1MB memcpy；g_dec_dw/dh 全删。
