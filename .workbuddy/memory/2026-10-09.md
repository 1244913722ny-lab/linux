## "Starting kernel" 黑屏根因已定位（earlycon 直 boot 验证）
- 用 `qemu -kernel zImage -dtb vexpress-v2p-ca9.dtb -initrd rootfs.img -append "...earlycon=pl011,0x10009000..."` 直 boot（绕过 U-Boot）后内核**正常起到用户态**：证明内核本身没问题。

- 运行内核已带 CONFIG_OF_CONFIGFS：日志出现 `of_cfs_init: OK` 与 `System initialized with ConfigFS DTO support`，确认之前 drivers/of/configfs.c 删 `#include <linux/of_resolver.h>` 的修复已生效、configfs 插件支持可用。

## LCD 不变色排查：fb0 写入成功但屏幕不动（DRM PL111 路径）
- testSDL.c 内核模块硬编码帧存 0x4c000000 → vexpress-a9 上既非 RAM 也非 PL111，写入被 QEMU 丢弃，"fill red done" 假象。DTB 实际 clcd@10020000，帧存由 DRM 动态分配。
- 用户自写用户态 fbdev 程序：`bpp=16 xres=1024 yres=768 smem_len=1572864(=1024*768*2)` 全对，readback=0xF800 成功；`echo 0 > blank` 无效(blank 为空)、`cat /dev/urandom > /dev/fb0` 报 ENOSPC(=先写满 total_size 再越界，属正常)——**数据确实写进了 fb0 缓冲，但 SDL 窗口纹丝不动（黑屏+一条静止白竖线）**。
- 链路核实（树内证据）：DTB clcd endpoint 经 remote-endpoint=&lt;0x13&gt; 连 I2C `sil,sii9022-tpi`@0x39 DVI 桥；pl111 DRM 驱动(drivers/gpu/drm/pl111/pl111_drv.c:109-168) 硬性要求 panel/bridge 否则 "No bridge, exiting"=-ENODEV。fb0 能以 1024×768 创建 → sii9022 大概率已 bind、管线在。
- 主嫌疑：5.0.17 用 `drm_fbdev_generic_setup`(pl111_drv.c:332) → generic fbdev = **影子缓冲+deferred I/O**，写 fb0 先落 shadow，靠 dirty flush 搬到被扫描的 GEM 缓冲；flush/atomic commit 失败即出现"写成功、屏幕不动"假象。待用户 guest dmesg 验证。
- 备用路线 B：老 fbdev `CONFIG_FB_ARMCLCD`(amba-clcd) 需 clcd 节点含 "panel-timing"（clcdfb_of_init 用 of_get_display_timing），当前 DTB clcd@10020000 **没有 panel-timing**，切驱动需同时 overlay 补 panel-timing，较麻烦。

## LCD 不变色续：vram 非活跃扫描缓冲(devmem 实测)+ 终端测试法
- **更正此前误判**: `0x4c000000`(vram@4c000000) **不是**活跃显示正在扫的缓冲。DTB 中 `memory-region=<&vram>` 挂在主板 CLCD(=dmesg `1001f000.clcd` 'core tile graphics' 且 'this device will be deactivated'); 真正出图到 SII9022→SDL 的是 `10020000.clcd`(DTB 节点 grep 确认**无 memory-region**)→ 帧存从系统 RAM 的 CMA 分配(物理在 0x6xxxxxxx 一带)。
- 实测佐证: 用户 `devmem 0x4c000000 32 0xF800F800` 与 `devmem 0x4c010000 ...` 均**无变化** → 活跃 PL111 不扫 vram 区。testSDL.c 写 0x4c000000 是写错了(被停用核心板的)vram, 非地址偏移问题。
- 5.0.17 无 `dri/0/gem` debugfs(CMA 只提供打印函数未挂文件); `dri/0/state` 的 `obj[0].start=00010000` 是 GEM 的 vma 假偏移(`drm_vma_node_start`), **非物理地址**。/dev/fb0 的 smem_start=0, 也无法从 debugfs 取真实扫描 paddr。
- **纯终端(免编译)测试法**: ① `printf '\033[2J\033[41mHELLO\033[0m\n' > /dev/tty0`(fbcon 绑帧缓冲则 SDL 出红/文字, 证 fb0 被扫描); ② `dd if=/dev/urandom of=/dev/fb0 bs=4096 conv=fsync`(`conv=fsync` 触发 fb_deferred_io_fsync, 或逼出 shadow→GEM 搬运)。两者都无效则 fb0 在该组合不通, 需走 DRM dumb-buffer ioctl(`/dev/dri/card0`, 裸 ioctl 无需 libdrm)。

## LCD 显示打通: 两层原因(最终澄清)
- **实际修复 = QEMU 显示后端 `-display sdl` → `-display gtk`**(start_uboot.sh 第10行已改)。本环境 QEMU 跑在 WSL/Windows 上, `sdl` 后端渲染的是**一帧冻结画面**(只捕获初始帧=那条白竖线残影, 不响应 framebuffer 后续更新)→ 这就是"写啥都屏幕不动"的视觉主因, 纯属主机侧渲染问题, 与 guest fb0 的 flush 机制无关。换 `-display gtk` 后 QEMU 正常按 PL111 刷新, 写入立即可见。
- **guest 侧 fb0 仍有 deferred-I/O 搬运问题**(独立一层): 5.0.17 用 `drm_fbdev_generic_setup` → generic fbdev = 影子缓冲+deferred I/O。裸 mmap 写 fb0 后须 `msync(fb, smem_len, MS_SYNC)`(或 `fsync(fd)`)才搬到被扫描的 GEM; 简单 app 写完直接 return 不过同步 → 即便后端正确也不上屏。GTK(用户态)走 GDK linuxfb 会自动 msync/fsync, 故它在正确后端下能亮。
- **结论**: "使用 gtk 可以" = ① QEMU 用 GTK 后端(画面会刷新) + ② 测试程序正确 flush(fb 写会上屏), 两层各解决一半。GTK 程序本身验证"显示管线通、fb0 确被 PL111 扫描"(否定了 fb0 是 ghost 的猜测)。
- **给简单 app 的一行修法**: mmap 填色后加 `msync(fb, f.smem_len, MS_SYNC);`(或 `fsync(fd);`)。
- **本环境铁律**: vexpress-a9 图形显示一律用 `-display gtk`, 禁用 `-display sdl`(冻屏)。
- 此前 `devmem 0x4c000000` 无反应, 是因 vram 属被停用核心板 CLCD, 与活跃显示无关; 活跃扫描缓冲在 CMA(0x6xxxxxxx), 5.0.17 无 debugfs 暴露其 paddr, 故盲打 devmem/ioremap 不可行, 应走 /dev/fb0(配 msync) 或 DRM dumb-buffer ioctl。
